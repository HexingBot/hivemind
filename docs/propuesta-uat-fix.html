Arreglar el sistema de verificacion UAT de hivemind — Propuesta

Para Mato · repositorio HexingBot/hivemind v0.22.0 · diagnostico verificado en el codigo, sin cambios aplicados

1 · El problema

Los UAT se crean pero no se completan ni se corren. La regla que exige un UAT valido antes de cerrar un ticket vive unicamente en la documentacion; ningun punto del codigo la hace cumplir. Resultado: un ticket puede llegar a done sin que nadie haya verificado nada, y el sistema no se entera.

La evidencia es numerica y separa limpiamente los dos regimenes:

9 / 9 Donde el sensor es incondicional (tier uat-only, reviewer.md): cumplimiento total.
7 / 16 se fugan Donde el sensor es condicional (tier tests-after): casi la mitad cierra sin UAT.
0 Puntos del codigo, comandos o jobs de CI que puedan negar un cierre sin UAT.

La lectura es directa: el problema no es la disciplina de los agentes, es que la regla no es mecanica. Donde no hay eleccion, se cumple; donde hay criterio, se fuga.

2 · Causas raiz (verificadas en el repo)

  1. El gate UAT solo existe en documentacion (CLAUDE.md, reviewer.md) — ninguna linea de codigo se niega a cerrar un ticket sin UAT completo.
  2. El UAT es prosa libre, sin esquema — cada autor lo escribe distinto, asi que es imposible validarlo automaticamente.
  3. Cero CI — no existe .github/workflows; el gate lo corre el mismo agente que decide si aplica (conflicto de interes puro).
  4. El MCP de tareas se cae (CONNECTION_CLOSED) y el fallback edita JSON a mano, saltandose la capa donde vivirian los gates.
  5. Triple duplicacion mantenida a mano (agents/ ↔ .claude/agents/, skills/, workflows/) — fuente constante de drift entre lo que se lee y lo que corre.
  6. dist/*.cjs son artefactos committeados cuyo gate de frescura solo corre en release: entre releases se puede publicar un bundle viejo en silencio.
  7. transitionStatus / appendComment no son race-safe (src/task-store.js): dos sesiones concurrentes pueden pisarse los cambios.

3 · La propuesta, paso a paso

1 UAT con esquema, no prosa

Que hace
Cada UAT pasa a ser un objeto JSON estructurado: una lista de pasos con id, accion, resultado_esperado, resultado_observado, veredicto (PASS o FAIL) y notas, cubriendo cada criterio de aceptacion del ticket.
Por que importa
Es el cimiento de todo lo demas: nada se puede validar mecanicamente mientras el UAT sea un parrafo escrito a gusto de cada autor.
Como se ve
Un UAT real, legible por humano y por maquina:
{
  "ticket": "TASK-220",
  "acceptance_criteria": ["AC1", "AC2"],
  "pasos": [
    {
      "id": "1",
      "cubre": "AC1",
      "accion": "npm run uat -- TASK-220",
      "resultado_esperado": "sale 0 y valida los 2 AC",
      "resultado_observado": "exit 0, 2/2 AC cubiertos",
      "veredicto": "PASS",
      "notas": ""
    },
    {
      "id": "2",
      "cubre": "AC2",
      "accion": "cerrar el ticket sin UAT valido",
      "resultado_esperado": "transitionStatus lanza error",
      "resultado_observado": "cerro igual",
      "veredicto": "FAIL",
      "notas": "el gate no esta conectado"
    }
  ],
  "overall": "FAIL"   // se deriva, no se escribe a mano
}

2 Un comando unico: npm run uat

Que hace
Valida el esquema y falla (exit distinto de 0) si un UAT no cubre todos los criterios de aceptacion, si algun paso tiene FAIL, o si a algun paso le falta el resultado observado.
Por que importa
Convierte la regla en una fuente de verdad mecanica: deja de depender del juicio del agente de turno. El overall se calcula, nadie lo declara.
Como se ve
npm run uat -- TASK-220 → FAIL: paso 2 en FAIL; AC2 sin cobertura valida. Exit 1.

3 El gate vive en el codigo, no en los docs

Que hace
transitionStatus hacia done lanza error si el ticket requiere UAT y no tiene un artefacto UAT valido. Se implementa en src/task-store.js, no en el MCP.
Por que importa
Ataca la causa raiz #1 y ademas la #4: si el gate viviera en el MCP, se evaporaria cada vez que el MCP se cae y el fallback escribe JSON a mano. En el task-store, toda ruta de escritura pasa por el.
Como se ve
Error: no se puede pasar TASK-220 a done: falta UAT valido (AC2 sin cobertura).

4 CI basico que juzgue desde afuera

Que hace
Un .github/workflows/ci.yml que en cada push corre npm test mas el gate UAT sobre todo el board: ningun ticket en done puede quedar sin UAT completo.
Por que importa
Elimina el conflicto de interes de la causa #3. Hoy el mismo agente que decide si el gate aplica es el que lo corre; con CI, un tercero neutral emite el veredicto y queda registrado.
Como se ve
Check rojo en el PR: UAT gate: 3 tickets done sin UAT valido (TASK-204, TASK-211, TASK-219).

5 Cerrar la fuga del tier tests-after

Que hace
Ahi esta la fuga real (7 de 16). Dos salidas, hay que elegir una: (a) exigir UAT siempre que los criterios de aceptacion sean observables por un humano, o (b) definir un mecanismo de excepcion explicito, registrado en el ticket y con aprobacion humana.
Por que importa
Es el unico paso que toca la politica y no solo la mecanica. Lo inaceptable es el estado actual: una excepcion implicita que nadie declara y nadie audita.
Como se ve
Campo nuevo en el ticket: uat_exempt: true con uat_exempt_reason y approved_by obligatorios; sin los tres, el gate del paso 3 no perdona.

6 El MCP como fachada opcional

Que hace
Se deja explicito que el gate vive en el task-store y que el MCP es solo una fachada delgada sobre el; se documenta el fallback manual para que no exista una ruta que salte la validacion.
Por que importa
Mientras el MCP siga cayendose, el camino degradado es el camino habitual — y hoy es justo el que no valida nada.
Como se ve
Editar el JSON a mano sigue siendo posible, pero el gate de CI (paso 4) lo detecta en el siguiente push.

7 Des-duplicar agents / skills / workflows opcional

Que hace
Elegir UNA fuente de verdad para cada par duplicado; la copia se genera en build en lugar de mantenerse a mano.
Por que importa
Elimina la causa #5 de raiz: hoy la regla puede estar corregida en una copia y vieja en la otra, y el agente lee la vieja.
Como se ve
Un test de paridad falla si las copias divergen — mismo patron que el gate de frescura de dist/, pero corriendo siempre, no solo en release.

4 · Que ganas con esto

  • Los UAT se corren de verdad. Un comando unico los ejecuta y los valida; dejan de ser un texto que se escribe y se olvida.
  • Nadie cierra sin verificar. El gate esta en el codigo, en la unica capa por la que pasan todas las escrituras — no en un parrafo que un agente puede no leer.
  • El CI juzga sin conflicto de interes. Quien hace el trabajo deja de ser quien decide si el trabajo se verifico.
  • Un ticket en done vuelve a significar algo. El estado del board pasa a ser evidencia auditable en vez de una afirmacion de confianza.
